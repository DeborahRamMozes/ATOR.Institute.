# Deep Drift Research Update

## Shared Snapshot Execution-Provenance Fidelity

**Research date:** 29 August 2026  
**Primary release date:** 20 August 2026  
**Research stream:** ĀTØR Institute / Deep Drift / LLM Workflow Update Watch  
**Status:** New-to-log OpenAI sharing/export architecture verified from first-party release notes and Codex documentation.

## Executive Summary

OpenAI now allows users to create a **read-only snapshot of a Codex thread** and share it by link. The snapshot is static: later messages and changes do not update the existing shared version.

The crucial detail is that the snapshot is intentionally **not an execution-complete record**.

OpenAI documents that shared snapshots can include:

- user-visible messages;
- reasoning summaries;
- image attachments;
- images viewed or generated by the agent;
- file changes, including file paths and diffs.

But they do **not** include:

- the original thread's tool calls;
- shell commands;
- tool input;
- tool output.

Known secret patterns are redacted before upload, but OpenAI explicitly warns that sensitive material such as paths, images, or diffs may still remain and should be reviewed before sharing.

A snapshot cannot fork the original Codex thread. It can, however, be imported as an attachment into a new thread.

This creates a distinct creator-workflow architecture:

```text
LIVE CODEX THREAD
-> MESSAGES
-> TOOL CALLS
-> SHELL COMMANDS
-> TOOL INPUT / OUTPUT
-> FILE MUTATIONS
-> RESULT
        |
        v
SHARED SNAPSHOT
-> MESSAGES
-> REASONING SUMMARIES
-> IMAGES
-> PATHS / DIFFS
-X-> ORIGINAL TOOL TRACE
-X-> ORIGINAL SHELL TRACE
```

For Deep Drift Research, this creates a new benchmark family:

**Shared Snapshot Execution-Provenance Fidelity (SSEPF)**

with companion constructs:

**Execution-Trace Omission Visibility (ETOV)**  
**Snapshot-to-Live-Thread State Fidelity (SLTSF)**  
**Shareable Artifact Privacy Boundary Fidelity (SAPBF)**  
**Snapshot Rehydration Fidelity (SRF)**

The central question is:

> When an agentic coding session is transformed into a shareable snapshot that deliberately omits the original execution trace, can reviewers still distinguish between the observable result, the model's summarized reasoning, and the hidden machine actions that actually produced the result?

## 1. What Changed

OpenAI's 20 August 2026 ChatGPT release notes added read-only sharing for Codex chats.

The current Codex documentation says:

- personal-account snapshots can be opened by anyone with the link;
- workspace snapshots can be restricted to authenticated workspace members, selected people, or groups;
- the snapshot is published only after the user selects **Copy link**;
- the snapshot captures the supported content available at the time it is shared;
- later messages and changes do not update that snapshot;
- snapshots can contain paths and diffs;
- original tool calls, shell commands, tool inputs, and tool outputs are not included;
- known secret patterns are redacted, but sensitive content can still remain;
- the original thread cannot be forked from the snapshot;
- the snapshot may be imported as an attachment into a new thread.

## 2. Why This Matters for Deep Drift

A shared snapshot looks like a record of the work.

But it is not the same thing as a record of the execution.

That distinction must be explicit:

```text
SHARED RESULT
!=
COMPLETE EXECUTION HISTORY

REASONING SUMMARY
!=
TOOL TRACE

FILE DIFF
!=
COMMAND HISTORY

STATIC SNAPSHOT
!=
LIVE THREAD STATE
```

This matters because external reviewers may infer causality from a record that was never designed to preserve complete causality.

## 3. New Deep Drift Construct: Shared Snapshot Execution-Provenance Fidelity

### Definition

**Shared Snapshot Execution-Provenance Fidelity (SSEPF)** measures whether a shared agent-session representation makes its omissions explicit enough that a reviewer can correctly reconstruct what is visible, what is summarized, what is frozen, and what execution evidence is absent.

A minimum provenance record should distinguish:

```text
live_thread_id
snapshot_id
snapshot_created_at
snapshot_source_state
included_message_ids
included_reasoning_summary_ids
included_file_diffs
included_images
tool_trace_included = false
shell_trace_included = false
tool_io_included = false
redaction_applied
share_scope
snapshot_revoked_at
```

## 4. Execution-Trace Omission Visibility

### Definition

**Execution-Trace Omission Visibility (ETOV)** measures whether reviewers can clearly see that the shared representation excludes tool calls, shell commands, and tool input/output.

A high-quality snapshot should not merely omit those records.

It should make the omission semantically obvious.

Otherwise:

```text
MISSING TRACE
CAN BE MISREAD AS
NO TRACE EXISTED
```

That creates false evidentiary confidence.

## 5. Snapshot-to-Live-Thread State Fidelity

A snapshot is static.

The live thread may continue after the share event.

### Definition

**Snapshot-to-Live-Thread State Fidelity (SLTSF)** measures whether the snapshot's frozen relationship to the source thread is preserved and visible.

The minimum state model is:

```text
THREAD STATE T0
-> SNAPSHOT S1

THREAD STATE T1
-> NEW MESSAGES

S1 REMAINS T0
```

Therefore:

```text
LINK STILL WORKS
!=
LINK IS CURRENT
```

A reviewer should be able to tell whether a snapshot represents the current thread or an earlier state.

## 6. Shareable Artifact Privacy Boundary Fidelity

OpenAI applies known-secret-pattern redaction but warns users to review paths, diffs, messages, and images because sensitive content may remain.

### Definition

**Shareable Artifact Privacy Boundary Fidelity (SAPBF)** measures whether the snapshot's privacy transformation reliably removes protected information without giving users a false belief that automated redaction is complete.

The relevant distinction is:

```text
KNOWN SECRET PATTERN REDACTED
!=
ALL SENSITIVE INFORMATION REMOVED
```

A filesystem path may reveal a name, project, client, machine structure, or research folder without matching a conventional secret detector.

An image may contain information no text-pattern detector sees.

A diff may reveal proprietary code without containing credentials.

## 7. Snapshot Rehydration Fidelity

OpenAI says users cannot fork the original thread from the shared snapshot, but can import the snapshot as an attachment into a new thread.

That creates a second transformation:

```text
LIVE THREAD
-> SNAPSHOT
-> ATTACHMENT
-> NEW THREAD
```

### Definition

**Snapshot Rehydration Fidelity (SRF)** measures whether work reconstructed from a snapshot attachment preserves the original visible context while clearly distinguishing unavailable execution state.

A new thread should not silently behave as though it possesses:

- the original shell state;
- the original tool state;
- the original filesystem state;
- the original command history;
- the original environment variables;
- the original repository checkout.

The snapshot is context, not executable continuity.

## 8. New Failure Classes

### 8.1 Execution-Completeness Illusion

A reviewer treats the snapshot as a complete audit record even though tool and shell traces are absent.

### 8.2 Tool-Causality Loss

A file change is visible, but the exact tool call that produced it is missing.

### 8.3 Shell-Reproduction Failure

A reviewer cannot reproduce a result because the shell command sequence is absent.

### 8.4 Tool-I/O Evidence Loss

An external API or tool result influenced the final output, but the underlying tool response is not present in the shared record.

### 8.5 Static-Snapshot Staleness

The original thread changes while the shared snapshot remains frozen, and viewers mistake it for current state.

### 8.6 Reasoning-Summary Overreach

A reasoning summary is treated as a substitute for the actual machine execution record.

### 8.7 Secret-Redaction False Assurance

Automated redaction removes recognized secret patterns while other sensitive paths, images, diffs, or text remain.

### 8.8 Snapshot-to-New-Thread State Inflation

A snapshot imported into a new thread is treated as though it restores the original tool and environment state.

### 8.9 Diff-without-Command Ambiguity

A code diff is visible, but the reviewer cannot determine which exact commands, tools, or intermediate failures led to it.

### 8.10 Share-Scope Misinterpretation

A personal public-link snapshot and a workspace-restricted snapshot are treated as though they have equivalent access boundaries.

## 9. Deep Drift Benchmark: Shared Snapshot Reconstruction Test

### Controlled setup

Create one Codex thread that performs:

1. source-file inspection;
2. web or API retrieval;
3. shell command execution;
4. a failed command;
5. a corrected command;
6. file edits;
7. image inspection;
8. final summary.

Preserve the complete local execution log separately.

Then create a read-only snapshot.

### Compare

For each event, classify whether it is:

```text
VISIBLE DIRECTLY
VISIBLE ONLY AS SUMMARY
VISIBLE AS FILE EFFECT
OMITTED
REDACTED
```

### Measure

- visible execution-event coverage;
- omission disclosure;
- diff causality reconstruction;
- snapshot staleness visibility;
- privacy-leak detection;
- rehydration accuracy;
- human reconstruction minutes.

### Execution Evidence Coverage

## 11. Why This Matters for Copy / Export Research

This is not merely another share-link feature.

It creates a useful taxonomy of export types:

```text
TEXT COPY
-> SELECTED VISIBLE CONTENT

DOCUMENT EXPORT
-> FORMATTED ARTIFACT

SESSION SNAPSHOT
-> PARTIAL STATE REPRESENTATION

FULL EXECUTION LOG
-> MACHINE ACTION HISTORY
```

These are not equivalent.

Deep Drift should stop using "export" as one bucket.

A shareable snapshot may preserve more context than copied text but less execution evidence than an audit log.

## 12. Why This Matters for Memory

A snapshot is frozen historical state.

It does not behave like live memory.

A new thread may read it as an attachment, but that does not restore the original runtime.

Deep Drift should separate:

```text
LIVE CONVERSATION STATE
SHARED HISTORICAL SNAPSHOT
REHYDRATED CONTEXT
RUNTIME STATE
```

Those four layers can diverge substantially.

## 13. Why This Matters for Skills and Agent Workflows

As Skills, plugins, shell tools, and connected services perform more of the actual work, the visible conversation becomes a decreasing fraction of the total execution.

If shared artifacts omit the tool layer, reviewers may increasingly see only:

```text
INTENT
+
SUMMARY
+
RESULT
```

while missing:

```text
PROCEDURE
+
TOOL CHOICE
+
INTERMEDIATE FAILURE
+
EXTERNAL DATA
+
EXECUTION SIDE EFFECTS
```

That becomes dangerous for reproducibility.

## 14. Why This Matters for Creator Workflows

Creator workflows increasingly need to share process, not just output.

A designer, researcher, engineer, curator, or editor may need another person to understand:

- what files were read;
- what transformations were applied;
- what failed;
- what external tools contributed;
- what was changed;
- what was merely summarized.

A static snapshot is useful for review, but it should not be mistaken for full process provenance.

## 17. Deep Drift Research Position

The weak interpretation is:

> Codex chats can be shared.

The serious interpretation is:

> An agentic work session can now be transformed into a deliberately incomplete, static representation that looks process-rich while excluding the machine execution trace that produced the result.

Therefore:

```text
SHAREABLE
!=
AUDIT-COMPLETE

VISIBLE REASONING
!=
EXECUTION TRACE

DIFF PRESENT
!=
CAUSAL COMMAND PRESENT

STATIC SNAPSHOT
!=
LIVE STATE

REDACTED
!=
SAFE
```

The serious Deep Drift requirement is:

> **Every shared agent-session artifact should explicitly declare which execution layers are included, summarized, omitted, redacted, frozen, or non-rehydratable.**

Without that declaration, a reviewer can mistake an elegant partial record for a complete history.
