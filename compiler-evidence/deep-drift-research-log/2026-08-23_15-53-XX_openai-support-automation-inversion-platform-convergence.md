# II. ENGLISH CONTROL VERSION

## 1. Object under examination

The last OpenAI complaint did not concern one bad answer. It concerned the execution chain:

`human intent -> capability discovery -> tool selection -> permission -> execution -> verification -> delivery`

ATOR-QC-OPENAI-2026-002 named the central failure **Automation Inversion**. The machine may possess, expose, or sit near the needed capability, yet the human becomes tool finder, terminology translator, state carrier, surface router, debugger, and integration middleware.

The operative question was plain: if the machine has the capability, why is the human still serving as the integration layer?

## 2. Support correction

Human support supplied a necessary architectural correction. GPT Actions connect a GPT to an external API and require API details, authentication, and an OpenAPI schema. Apps and Actions remain separate configurations. A Custom GPT can use one or the other, not both simultaneously. An app connected elsewhere in ChatGPT does not thereby become the backend for a Custom Action.

This correction narrows the original claim. The Supabase episode cannot be classified in its entirety as routing failure without first identifying which execution surface was active.

The broader research problem survives the correction. A technically valid boundary can still create human orchestration burden when the user must understand internal product topology before an ordinary intent can be completed.

## 3. Relation to current creator-workflow direction

OpenAI's current platform direction increasingly packages workflows above those boundaries. ChatGPT Work operates across connected apps and files and can produce finished artifacts. Plugins can package skills, apps, and app templates. The official plugin documentation describes the plugin layer as a means of completing repeatable workflows without manually switching among separate tools.

This is a strong conceptual relation to HOBR, ALI, and ECUR.

It is not evidence of causal influence from the ATØR complaint. ChatGPT Work and the Plugin Directory were announced on 9 July 2026, before the 14 August follow-up report. Any claim that the complaint caused those releases would fail chronology.

The presently documented Apps/Actions separation also remains. Product convergence at the workflow surface therefore coexists with architectural separation at the execution layer.

# III. HYPOTHESIS SET

## Hypothesis A: Workflow Abstraction Hypothesis

**Claim:** Packaging apps, skills, templates, approvals, and artifact creation into higher-level workflows can reduce HOBR and ALI if the system discovers and routes capabilities before instructing the human to perform intermediate technical work.

**Mechanism:** internal capability registry -> permission check -> route selection -> execution -> verification.

**Prediction:** comparable tasks should require fewer manual routing steps in Work/plugin workflows than in manually assembled Custom Action workflows.

**Supporting evidence:** current product architecture packages workflow guidance and apps inside plugins and enables longer execution through Work.

**Contradicting evidence:** Custom GPT Apps/Actions remain mutually exclusive; permissions and surface availability still constrain execution.

**Failure condition:** HOBR and ALI do not decrease in controlled non-engineer tasks despite increased plugin/work capability.

## Hypothesis B: Surface Convergence / Runtime Fragmentation Hypothesis

**Claim:** user interfaces may converge faster than underlying execution architectures.

**Mechanism:** a unified surface presents apps, skills, files, and agents together while permission, runtime, backend, and product-class boundaries remain distinct.

**Prediction:** users will perceive a capability as "available" even when it is unavailable in the active execution context.

**Failure condition:** platform capability introspection reliably tells users what can execute, where, and why before manual troubleshooting begins.

## Hypothesis C: Support-as-Architecture-Probe Hypothesis

**Claim:** support correspondence can reveal product boundary conditions that ordinary interface language leaves obscure.

**Mechanism:** technical support distinguishes designed limitation from routing defect and requests a narrow reproduction.

**Prediction:** narrow reproductions will separate architecture constraints from actual tool-selection failures more reliably than broad complaint narratives.

**Failure condition:** the same reproducible configuration behaves inconsistently despite the documented boundary conditions.

## Mundane Rival

The observed burden may arise chiefly from the inherent complexity of connecting secure external systems. APIs, authentication, schemas, and permission boundaries cannot always be abstracted away without sacrificing control or security.

**Test:** compare engineer and non-engineer completion under the same secure workflow, with and without an intent-first abstraction layer. If error and completion gaps remain unchanged, the abstraction hypothesis weakens.
