# Deep Drift Research Update - CMPF

## Cross-Provider Memory Portability Fidelity

**Research date:** 4 September 2026  
**Primary fresh delta:** Anthropic updated its first-party memory import/export documentation on 4 September 2026. Claude now explicitly supports moving memory between AI providers by asking the source system to emit its stored memory/context, then importing that text into Claude, where Claude extracts key information into individual memory entries. Anthropic states that imports are experimental and may not always successfully incorporate imported memories.

## Executive finding

Memory has become a portable creator asset.

But portability is not equivalence.

```text
SOURCE PROVIDER MEMORY
        |
        v
SOURCE-PROVIDER EXPORT / SELF-REPORT
        |
        v
TEXT TRANSFER
        |
        v
CLAUDE IMPORT PARSER / INTERPRETER
        |
        v
NEW MEMORY ENTRIES
```

Therefore:

```text
EXPORTED MEMORY
!= SOURCE MEMORY STATE

IMPORTED MEMORY
!= EXPORTED MEMORY VERBATIM

SAME HUMAN CONTEXT
!= SAME MACHINE REPRESENTATION

PORTABLE
!= LOSSLESS

MEMORY TRANSFER
!= MEMORY CLONING
```

The new provenance object is the **memory translation chain**.

## 1. Memory export may be generated by the source model itself

Anthropic's recommended migration process begins by asking the previous AI provider to list every stored memory and learned context in one transferable block.

This is significant because the exported object may be a model-generated representation of memory rather than a canonical database dump.

```text
INTERNAL MEMORY STATE
-> MODEL SELF-REPORT
-> EXPORT TEXT
```

The model can therefore become an interpreter of its own memory before another model interprets the export.

Deep Drift should not collapse those layers.

## 2. Memory import is an extraction process, not a byte-for-byte restore

Anthropic says users paste exported memory into Claude and Claude extracts key information into individual memory entries.

The target memory is therefore reconstructed through a semantic transformation:

```text
EXPORT TEXT
-> EXTRACTION
-> NORMALIZATION
-> TARGET MEMORY ENTRIES
```

Memory migration is closer to translation than disk cloning.

## 3. Import success does not prove complete incorporation

Anthropic describes imports as experimental and says Claude may not always successfully incorporate imported memories.

```text
TRANSFERRED
INCORPORATED
VERIFIED
```

These must not be represented by one boolean field such as `memory_imported=true`.

## 4. Provider policy can transform the imported corpus

Claude memory focuses on work-related topics and may not retain imported personal details unrelated to work.

```text
SOURCE MEMORY CORPUS
-> TARGET POLICY FILTER
-> TARGET MEMORY CORPUS
```

Even a perfect export can become a deliberately non-identical import because the target provider applies its own memory policy.

## 5. Human redaction is part of the migration chain

Anthropic encourages users to customize the export prompt to exclude sensitive information before importing.

```text
SOURCE EXPORT
-> HUMAN REDACTION / EDIT
-> TARGET IMPORT
```

The final target memory can therefore differ because of intentional human filtering.

## 6. Memory becomes cross-platform creator infrastructure

Accumulated working preferences, project details, formatting expectations, terminology, corrections, and recurring goals can now be intentionally moved between AI ecosystems.

```text
MODEL SWITCH
USED TO IMPLY
CONTEXT REBUILD

NOW:
MODEL SWITCH
CAN INCLUDE
CONTEXT MIGRATION
```

Comparative personalization tests must record whether a model began from zero context, native accumulated memory, imported memory, or manually reconstructed memory.

## 7. Migration has multiple independent loss stages

A migration can lose information at export, import, and later retrieval/use.

```text
EXPORT LOSS
IMPORT LOSS
RETRIEVAL / USE LOSS
```

A completed import UI cannot measure all three.

## 8. Post-import behavior is the real test

Memory portability should be verified behaviorally by asking equivalent tasks before and after migration and comparing fact retention, instruction retention, priority retention, relationship retention, and behavioral application.

## 9. Memory and chat history are separate systems

Anthropic distinguishes past-chat search, which uses visible RAG tool calls over conversation history, from persistent memory topics.

```text
MEMORY PORTABILITY
!= CHAT-HISTORY PORTABILITY
```

A migrated user may preserve distilled context while losing access to the original conversations that justified it.

## 10. Scope translation matters

Claude gives each project a separate memory space and project summary. Cross-provider migration therefore needs scope mapping. If source scopes collapse into one target namespace, facts may survive while their boundaries do not.

## 11. Surface consumption matters

Anthropic states that memory is shared between Chat and Cowork when Cowork runs in the cloud, while local Cowork sessions do not use memory.

```text
MEMORY EXISTS + CLOUD COWORK -> MEMORY AVAILABLE
MEMORY EXISTS + LOCAL COWORK -> MEMORY NOT USED
```

A migrated memory can exist successfully and still not affect a downstream task if the execution surface does not consume it.

## 12. Legacy migration has a temporary recovery window

Anthropic says users who believe something was forgotten during the legacy-memory migration can export legacy memory until 9 September 2026 and paste missing portions back into Claude.

This is a migration-recovery event, not ordinary memory editing.

## 13. Markdown/text becomes a memory transport container

Anthropic notes that users can ask a source provider to export memory as Markdown for local backup.

```text
MEMORY
-> MARKDOWN / TEXT BACKUP
-> COPY / FILE TRANSFER
-> IMPORT
```

PDF is useful for human audit; machine-readable Markdown/text is better suited to round-trip migration testing.

## New failure classes

### Portability-Equals-Cloning Fallacy
Assuming imported memory is an exact duplicate of source memory.

### Self-Report-Equals-Database Fallacy
Treating a model-generated memory export as a canonical dump of the source provider's internal memory state.

### Import-Success-Equals-Incorporation Error
Assuming a completed import UI proves every memory was stored.

### Policy-Filter Blindness
Treating omitted target memories as random failure when target memory policy intentionally excludes them.

### Memory-vs-History Collapse
Assuming imported memory includes the original searchable conversation archive.

### Scope-Collapse Error
Preserving facts while losing whether they belonged to a specific project, workspace, or global memory namespace.

### Surface-Consumption Blindness
Assuming imported memory influences every execution surface equally.

## Deep Drift benchmark additions

**Export Completeness Fidelity (ECF)** - How much source memory appears in the migration export?

**Import Incorporation Fidelity (IIF)** - How much exported context becomes actual target memory entries?

**Behavioral Memory Transfer Fidelity (BMTF)** - Does the target system apply migrated preferences, project facts, and corrections in equivalent tasks?

**Memory Scope Preservation Fidelity (MSPF)** - Are global/project/workspace boundaries preserved across migration?

**Memory-History Separation Fidelity (MHSF)** - Can migrated memory remain distinguishable from source chat history?

**Memory Surface Consumption Fidelity (MSCF)** - Which target surfaces actually consume imported memory?

## DRPA-1.0 protocol additions

### CROSS-PROVIDER MEMORY TRANSLATION RULE

> When memory is exported from one AI provider and imported into another, preserve the source memory state, export mechanism, export prompt or API, exported representation, target import mechanism, target extraction result, and post-import memory state separately. Memory portability must be modeled as translation, not cloning.

### MEMORY TRANSFER LOSS ACCOUNTING RULE

> Measure export loss, import loss, and later retrieval/use loss independently. A successful migration submission must not be treated as evidence of complete incorporation or complete behavioral use.

### MEMORY-SCOPE PRESERVATION RULE

> Preserve whether each memory item belonged to global memory, a project, workspace, conversation class, or other scope. If the target system cannot preserve the original scope, record the collapse explicitly.

### MEMORY-MIGRATION SNAPSHOT RULE

> Capture the target memory immediately after import and before substantial new interaction. Later automatic memory edits must remain distinguishable from the migrated T0 state.

### MEMORY-HISTORY SEPARATION RULE

> Imported persistent memory must not be represented as imported chat history unless the underlying conversations themselves were transferred and remain searchable. Distilled memory and source conversation evidence are separate provenance objects.

## Canonical Deep Drift requirement

> Treat cross-provider memory migration as a multi-stage semantic transformation. Preserve source state, export representation, human edits, target extraction, target policy filtering, target scope, immediate post-import state, and later behavioral use separately. Never describe a migrated AI as carrying "the same memory" without evidence that export, incorporation, scope, and behavior all survived.

## Deep Drift principle

> **A memory can travel without arriving intact.**

Operationally:

> **Compare the memory before export, after import, and at the moment the new model actually uses it.**
