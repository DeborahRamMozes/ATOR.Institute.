# NOEMA: FROM GPT / COMPILER FRICTION TO PLUGIN MIGRATION

**Research essay**  
**Recorded:** 23 September 2026  
**Status:** ITCH / PRE-FORMAL HYPOTHESIS — NOT CONCLUSION  
**Source basis:** NOEMA CONTRARIA — ITCH RECORD, 23 September 2026.

## The problem beneath the product change

The visible product change is a migration from GPTs toward plugins. The deeper question is architectural. A sophisticated user-built compiler is not merely a prompt. It can contain protocol hierarchy, routing rules, state models, provenance rules, artifact lineage, failure handling, tool-execution logic, testing procedures, and project-specific intellectual architecture.

The prior NOEMA work had already documented a recurring composition problem: conversation, compiler, skills or plugins, tools and connectors, state, artifacts, and provenance did not necessarily behave as one coherent working system. The later migration notice therefore intersects with an already documented design problem, but chronology alone does not establish causation.

The research question is narrower and more useful than a motive claim: **when advanced user-built compilers move into a platform-managed plugin architecture, what changes in portability, reproducibility, inspectability, operational accessibility, and control over procedural knowledge?**

## From prompt to procedural artifact

The distinction matters because a mature compiler can encode accumulated engineering decisions. Treating it as merely a prompt obscures the actual object being migrated.

The research frame therefore separates four claims that must not be collapsed into one:

1. the platform processes the compiler;
2. platform personnel can inspect the compiler;
3. other users can obtain the compiler;
4. other users can reproduce its functionality.

Each claim requires different evidence.

## The control boundary

The migration creates a useful test of the boundary between author-developed procedural knowledge and platform-managed execution.

The relevant layers are:

**CONVERSATION → COMPILER → SKILLS / PLUGINS → TOOLS / CONNECTORS → STATE → ARTIFACTS → PROVENANCE**

The question is whether modular execution increases capability while simultaneously changing who controls packaging, permissions, lifecycle, sharing, exportability, and reproducibility.

This is not an accusation. It is a provenance and governance problem.

## Hypothesis field

Three principal hypotheses remain live:

**A. Benign architectural migration.** The change primarily addresses product lifecycle, modularity, tool integration, and platform architecture.

**B. Capability governance.** Advanced procedural systems move into a more centrally governed execution surface with clearer platform-controlled permissions and lifecycle.

**C. Procedural-knowledge exposure.** Migration may create new pathways through which sophisticated user-built procedural architectures become easier to inspect, reproduce, extract, duplicate, or operationalize.

A mundane rival explanation remains available: this is simply technical retirement or migration of the previous GPT architecture, without a special relationship to advanced-user behavior or compiler sophistication.

No conclusion should be promoted beyond the evidence.

## Preservation before migration

The canonical pre-migration system must survive independently. Preserve the current NOEMA state, compiler instructions, reference files, chronology, QC reports, migration notice, tool and connector configuration, permission configuration, and a pre-migration behavioral test suite.

After migration, rerun the same tests and classify every layer as **PRESERVED / CHANGED / LOST / UNKNOWN**.

The decisive experiment is not whether the migrated plugin answers one question. It is whether the compiler survives as a system.

## Difference map

The post-migration comparison should examine:

- instruction fidelity
- reference-file availability
- tool availability
- connector behavior
- memory/state behavior
- provenance
- artifact generation
- permissions
- sharing
- exportability
- reproducibility
- newly exposed surfaces

A successful product migration is therefore not automatically a successful compiler migration.

## Surviving research question

> If advanced user-built compilers are migrated into a platform-managed plugin architecture, does the migration increase the portability and reproducibility of author-developed procedural knowledge, and what controls prevent unauthorized inspection, extraction, duplication or redistribution of that knowledge?

This remains an **ITCH / research question**, not a conclusion about OpenAI's motives or conduct.
