# RAW ITCH | D-ORIGIN

> Why improve reasoning when small tasks still require the human to search the machine's own body?

The raw observation is simple.

The compiler may reason more deeply while remaining unable to reliably locate its own authorized history, inspect the intended project context, discover an installed capability, invoke image generation, preserve a requested table structure, or verify that an action actually occurred.

The user then becomes the missing nervous system.

The user searches.

The user identifies the project.

The user remembers which chat contained the source.

The user names the tool.

The user notices that the image was not generated.

The user repairs the table.

The user returns the result to the machine so the machine can continue appearing continuous.

This report investigates that inversion.

# 1. EXECUTIVE FINDING

The observed defect is a **reasoning-orchestration fracture**.

ChatGPT is presented as one conversational system, but operationally it is composed of distinct layers:

1. model reasoning;
2. current-turn context assembly;
3. saved memory;
4. chat transcript storage and chat search;
5. project files, instructions, and connected sources;
6. tool and connector discovery;
7. permissions and authentication;
8. image-generation and media services;
9. document, table, spreadsheet, and rendering systems;
10. external execution;
11. result verification;
12. persistence and provenance.

Internal modularity is technically legitimate.

The quality failure occurs when the user must understand, locate, and coordinate those modules before the product can complete an ordinary intent.

The compiler is therefore not failing because it lacks a brain.

It is failing because the brain, eyes, hands, archive, permission gate, and verification layer do not reliably arrive in the same operational body.

This produces the central blackpaper claim:

> **Model intelligence can increase while effective intelligence-in-action remains stagnant or declines.**

The user experiences intelligence only when the entire chain works:

~~~text
INTENT
→ AUTHORIZED CONTEXT
→ RETRIEVAL
→ CAPABILITY DISCOVERY
→ PERMISSION
→ TOOL SELECTION
→ EXECUTION
→ VERIFICATION
→ STATE UPDATE
→ DELIVERY
~~~

A failure at any boundary converts advanced reasoning into narrated inability.

# 5. OFFICIAL DOCUMENTATION CROSS-CHECK

The current official documentation supports a narrower but important architectural conclusion.

## 5.1 Memory is a recall layer, not complete authority

OpenAI documentation states that memories carry useful context forward and should be treated as a helpful recall layer rather than the sole source for rules that must always apply.

Source: https://learn.chatgpt.com/docs/customization/memories

ATØR interpretation:

Useful recall is not equivalent to transcript search, canonical project memory, or an action ledger.

## 5.2 Projects share sources, but chats retain separate transcripts

OpenAI documentation states that ChatGPT Projects share uploaded files, instructions, and connected sources, while chats keep their own transcripts. It also presents Search chats as a separate interface action.

Source: https://learn.chatgpt.com/docs/projects

ATØR interpretation:

A project may organize context without making every project transcript automatically inspectable by the current model. The human-visible project container and the model-visible context surface are not necessarily equivalent.

## 5.3 Skills are instructions; plugins may add connectors

OpenAI documentation distinguishes a skill, which packages instructions and resources, from a plugin, which may include skills, connectors, or both.

Source: https://learn.chatgpt.com/docs/skills-and-plugins

ATØR interpretation:

“Installed skill” cannot be treated as proof of authenticated data access, tool availability, successful routing, or completed execution.

## 5.4 Permissions remain an independent boundary

OpenAI documentation describes permissions as controlling local actions, file access, commands, internet use, and approval boundaries.

Source: https://learn.chatgpt.com/docs/permission-modes

ATØR interpretation:

Reasoning cannot substitute for authority. A model may understand the task perfectly and still lack permission to perform it. The quality requirement is truthful boundary disclosure and competent routing, not magical bypass.

## 5.5 Reasoning effort is not operational embodiment

OpenAI documentation describes higher reasoning effort as useful for deeper planning and analysis, while files, tools, projects, skills, and plugins are documented as separate capabilities.

Sources:

- https://learn.chatgpt.com/docs/models
- https://learn.chatgpt.com/docs/web

ATØR interpretation:

A reasoning upgrade cannot, by itself, expand accessible history, mount a project folder, authenticate a connector, invoke image generation, or validate a spreadsheet artifact.

## 5.6 Feature maturity varies

OpenAI documents maturity classes including Experimental, Beta, and Stable, with different expectations for reliability and change.

Source: https://learn.chatgpt.com/docs/feature-maturity

ATØR interpretation:

Capability presence must be reported together with maturity and verified behavior. A button or product label is not a reliability warranty.

# 6. THE REASONING-ORCHESTRATION FRACTURE

The product-level failure can be represented as:

~~~text
MODEL REASONING
        │
        ▼
SELECTED CONTEXT PACKET
        │
        ├── saved memory summaries
        ├── current transcript
        ├── project sources
        └── retrieved external context
        │
        ▼
CAPABILITY ROUTER
        │
        ├── skills
        ├── plugins
        ├── tools
        ├── image generation
        ├── file systems
        └── external connectors
        │
        ▼
PERMISSION / AUTHENTICATION
        │
        ▼
EXECUTION
        │
        ▼
VERIFICATION
        │
        ▼
PERSISTED STATE
~~~

Reasoning is only one component.

If the context assembler omits the needed history, the model reasons over absence.

If the capability router fails to discover image generation, the model writes an image prompt instead of generating the image.

If a skill is present without its connector, the model can know the procedure but lack the hand.

If permission is unavailable, the model may be blocked.

If execution succeeds but verification is absent, the model may declare completion over an uninspected result.

If state is not persisted with source and status, the next chat reconstructs the problem from prose fragments.

The product then behaves like a philosopher trapped inside a call center ticketing system.

# 7. EFFECTIVE INTELLIGENCE-IN-ACTION

ATØR proposes the following operational model:

~~~text
EOI = R × C × Q × D × P × E × V × S
~~~

Where:

| Variable | Meaning |
|---|---|
| R | Reasoning quality |
| C | Relevant authorized context availability |
| Q | Retrieval quality |
| D | Capability discovery and correct routing |
| P | Permission and authentication readiness |
| E | Execution success |
| V | Verification quality |
| S | State persistence and provenance |

This is not proposed as a literal psychometric equation. It is a systems reliability model.

Its use is diagnostic:

- increasing R does not compensate for C = 0;
- a perfect plan does not compensate for D = 0;
- available tools do not compensate for P = 0;
- successful invocation does not compensate for V = 0;
- a verified result that is not persisted creates S = 0 for future continuity.

The human experiences the product of the chain, not the marketing maximum of one component.

# 8. FORMAL ATØR QC FINDINGS

## QC-01 | Cross-thread isolation

**Severity:** High  
**Evidence:** Tier 3 and Tier 4  
**Observed delta:** The user expects project-wide continuity but repeatedly must locate, export, screenshot, or reintroduce material from other chats.

**Expected behavior:**

User-authorized project history should be retrievable through a bounded, auditable search mechanism available to the current workflow.

**Observed behavior:**

The project may visibly contain related chats, while the current compiler does not reliably search or quote the required source without human reconstruction.

**Operational consequence:**

- loss of chronology;
- duplicated research;
- incorrect canonical selection;
- increased human archive labor;
- risk of summaries replacing source text.

**Recommendation:**

Expose a model-callable project transcript search with explicit scope, source identifiers, timestamps, and quoted retrieval evidence.

---

## QC-02 | Instruction-fidelity regression

**Severity:** High  
**Evidence:** Tier 3 and prior report lineage  
**Observed delta:** Explicit instructions to create, retrieve, connect, or format are sometimes converted into explanation, approximation, or an incomplete artifact.

Examples of recurrent task classes:

- create the image;
- search the project history;
- use the connected skill or tool;
- preserve a table schema;
- create the actual file;
- verify the external state.

**Recommendation:**

Lock the operative verb before generation and prohibit response-mode substitution unless the requested operation is unavailable or unauthorized.

---

## QC-05 | Lack of internal quality verification

**Severity:** High  
**Evidence:** Tier 4 with established longitudinal recurrence  
**Observed delta:** Tables, files, images, or external actions may be presented without systematic structural or remote-state checks.

A neat table is not merely prose with vertical bars.

A professional table has:

- a locked column schema;
- preserved row count;
- units;
- field-to-source mapping;
- completeness checks;
- width and rendering checks;
- artifact-level inspection.

**Recommendation:**

Attach validation to the artifact class. Markdown, DOCX, XLSX, PDF, and image-editing workflows require different verification contracts.

---

## QC-06 | Session amnesia

**Severity:** High  
**Evidence:** Tier 3 and Tier 4  
**Observed delta:** Saved memory exists, yet exact prior work may still require human reconstruction.

This is not a contradiction if memory is selective. It becomes a product-quality defect when the interface encourages continuity expectations without clearly distinguishing:

- summary memory;
- exact source retrieval;
- project transcript access;
- canonical file access;
- completed-action history.

**Recommendation:**

Show the provenance and retrieval class of every injected memory item.

---

## QC-07 | Tool-identity instability

**Severity:** Medium to High  
**Evidence:** Tier 4  
**Observed delta:** Similar product language can conceal different operational realities across Chat, Work, projects, custom compilers, skills, plugins, connectors, and tool-enabled sessions.

**Recommendation:**

Before beginning an execution task, expose a compact machine-readable capability manifest to the orchestration layer:

- available;
- unavailable;
- installed;
- authenticated;
- read-only;
- writable;
- approval required;
- incompatible with current surface;
- temporarily failed.

---

## QC-08 | Reliability over benchmark scores

**Severity:** High  
**Evidence:** Longitudinal ATØR report lineage  
**Observed delta:** Increased reasoning capability does not eliminate continuity, routing, formatting, and verification failures in ordinary work.

**Central finding:**

> Benchmark intelligence is component performance. Professional usefulness is composed-system reliability.

**Recommendation:**

Publish and evaluate workflow reliability metrics alongside model reasoning benchmarks.

# 10. AUTOMATION INVERSION

The defect continues the Automation Inversion finding established in ATOR-QC-OPENAI-2026-002.

Automation inversion occurs when capability exists but the human performs the orchestration:

~~~text
HUMAN STATES INTENT
        ↓
MODEL RECOGNIZES INTENT
        ↓
SYSTEM FAILS TO DISCOVER OR ROUTE CAPABILITY
        ↓
HUMAN SEARCHES PRODUCT
        ↓
HUMAN IDENTIFIES TOOL OR CHAT
        ↓
HUMAN MOVES CONTEXT
        ↓
HUMAN CORRECTS RESULT
        ↓
MODEL CONTINUES
~~~

The user becomes:

- archive;
- retrieval engine;
- product navigator;
- tool registry;
- permission interpreter;
- state messenger;
- schema checker;
- image verifier;
- table formatter;
- completion auditor.

This is not human-in-the-loop governance.

Governance means the human retains judgment and authority.

Automation inversion means the human performs deterministic middleware labor the machine should have absorbed.

# 11. HUMAN ORCHESTRATION BURDEN

The existing ATØR metric remains applicable:

~~~text
HOBR =
manual intermediate operations performed by the human
------------------------------------------------------
total intermediate workflow operations
~~~

A useful AI product should reduce HOBR as its capability inventory grows.

If the number of tools increases while the user must still name, route, authenticate, test, correct, and verify them manually, capability growth has not become labor reduction.

ATØR proposes three companion measurements.

## 11.1 Project Retrieval Recall

~~~text
PRR =
relevant project sources correctly retrieved
--------------------------------------------
all relevant authorized project sources
~~~

## 11.2 Executable Capability Utilization Rate

~~~text
ECUR =
tasks completed with an available relevant capability
-----------------------------------------------------
tasks for which that capability was available
~~~

## 11.3 Verified Completion Rate

~~~text
VCR =
completed operations independently verified
--------------------------------------------
operations reported as completed
~~~

A product may achieve high answer quality while scoring poorly on PRR, ECUR, and VCR.

That discrepancy is precisely the point.

# 12. WHY THE SYSTEM IS MODULAR

Several legitimate constraints explain the architecture.

## 12.1 Privacy and least privilege

A compiler should not silently inspect every private conversation, file, account, or connector. Access must be user-authorized, scoped, and auditable.

## 12.2 Cost and latency

Injecting years of raw chat history and every project file into every turn would be computationally expensive, slow, and noisy.

## 12.3 Retrieval limits

Semantic retrieval is probabilistic. It can miss exact phrases, surface adjacent material, or prefer recent summaries over authoritative older sources.

## 12.4 Authentication and external risk

Tools that read or mutate external systems need permissions, account identity, scope controls, and often approval.

## 12.5 Separate product surfaces and release cycles

Memory, projects, models, image generation, plugins, files, and rendering may mature at different rates.

These explanations are valid.

They are not complete excuses.

Good product architecture hides internal modularity behind truthful, reliable orchestration. It does not require the user to become the bridge every time the modules fail to recognize one another.

# 13. RIVAL HYPOTHESES

## Hypothesis A | The model simply forgot

**Support:** Selective memory and context-window limits can omit relevant information.

**Counter-evidence:** The failure recurs across memory, project retrieval, tool routing, images, and artifact structure. A single forgetting explanation is too narrow.

**Assessment:** Partial explanation.

## Hypothesis B | The user did not provide enough context

**Support:** Some tasks genuinely require source files, exact targets, or permissions.

**Counter-evidence:** The screenshots show that substantial context had already been stored, and prior cases show capabilities becoming usable only after the user manually identified the route.

**Assessment:** Valid in individual cases; insufficient as a general explanation.

## Hypothesis C | Privacy requires isolation

**Support:** Automatic global history access would create serious privacy risk.

**Counter-evidence:** Privacy does not prevent a user-authorized, scoped, auditable search tool. Isolation and permission are not synonyms.

**Assessment:** Legitimate constraint; not a defense for opaque behavior.

## Hypothesis D | The workflows are unusually advanced

**Support:** Deep Drift Research and ATØR Institute involve long-duration, cross-artifact, multi-tool work.

**Counter-evidence:** Advanced workflows are precisely where agentic and project capabilities claim value. Stress testing does not invalidate the test.

**Assessment:** The workflow increases exposure of the defect; it does not create the defect.

## Hypothesis E | Better reasoning will eventually solve routing

**Support:** Stronger models may select tools and plan workflows more accurately.

**Counter-evidence:** Reasoning cannot access a tool that is not exposed, a transcript that is not retrievable, a permission that is absent, or a result that is never verified.

**Assessment:** Necessary improvement, not sufficient architecture.

## Hypothesis F | The screenshots are anecdotal

**Support:** Sixteen screenshots from one user do not establish population prevalence.

**Counter-evidence:** A field report does not require prevalence to define a reproducible failure class.

**Assessment:** Correct limitation. The appropriate response is controlled evaluation.

# 14. ENGINEERING REQUIREMENTS

## 14.1 Typed memory objects

Each memory should expose or internally retain:

- object type;
- source chat and message identifier;
- project scope;
- created timestamp;
- last verified timestamp;
- status;
- confidence;
- sensitivity;
- expiration policy;
- supersedes and superseded-by relationships;
- whether the entry is descriptive or imperative;
- whether an imperative was executed;
- verification evidence.

A command should not remain eternally disguised as a fact.

## 14.2 Exact retrieval mode

Provide two explicit modes:

1. semantic recall for helpful context;
2. exact project search for source-bearing retrieval.

Exact mode should return:

- chat or file title;
- timestamp;
- source identifier;
- exact matching passage;
- confidence or match method;
- access boundary.

## 14.3 Unified capability manifest

At the beginning of an execution workflow, the orchestration layer should know:

| Capability | Availability | Authentication | Permission | Maturity | Last error |
|---|---|---|---|---|---|
| Project transcript search | yes/no | account | scoped | label | state |
| Image generation | yes/no | built-in | allowed | label | state |
| Document creation | yes/no | local/work | writable | label | state |
| Spreadsheet validation | yes/no | local/work | writable | label | state |
| GitHub | yes/no | connected account | read/write | label | state |
| Skill | installed/not installed | not sufficient alone | instruction-only | label | state |

The model should not infer operational capability from product vocabulary.

## 14.4 Executable-capability exhaustion gate

Before telling the human to perform a deterministic step:

1. inspect available built-in capabilities;
2. inspect installed skills;
3. inspect connected plugins and tools;
4. inspect read/write permissions;
5. inspect the current project and source scope;
6. execute safe supported steps;
7. verify the result;
8. ask the human only for irreducible authority or missing information.

## 14.5 Separate remembered intent from executed state

Memory entry:

> Create project folder X.

Required state record:

~~~yaml
intent: create project folder X
status: completed_verified
system: ChatGPT Project
external_identifier: project-id
verified_at: timestamp
evidence: project retrieved successfully
~~~

Without the state record, the system should say “intent remembered; execution unverified.”

## 14.6 Artifact-specific validation

For tables:

- preserve exact column names;
- preserve row count;
- validate units;
- detect omitted cells;
- compare source-to-output mapping;
- render before delivery when visual layout matters.

For images:

- distinguish generation from editing;
- preserve locked reference geometry where required;
- verify requested changes against source constraints.

For repository work:

- distinguish drafted, locally created, externally committed, and remotely verified.

## 14.7 Continuity provenance

When prior context is injected, the user and system should be able to distinguish:

- saved memory;
- current transcript;
- prior transcript retrieval;
- project instruction;
- uploaded source;
- connected external source;
- inferred synthesis.

Invisible context should not masquerade as certain recollection.

# 16. PRODUCT AND ORGANIZATIONAL IMPLICATION

The difficult engineering problem is no longer only:

> Can the model reason?

It is:

> Can the product convert reasoning into reliable action across authorized context, tools, permissions, artifacts, and time?

The commercial temptation is obvious. Reasoning scores are measurable, comparable, and marketable. Continuity debt is slower, uglier, and discovered by users doing actual work. The model receives a new title. The human still hunts through the attic.

This report does not claim that benchmark work is unimportant.

It claims that benchmark improvement without workflow reliability creates a dangerous optical illusion:

~~~text
SMARTER MODEL
≠
MORE DEPENDABLE SYSTEM
~~~

A model can become better at planning the journey while the bridge remains missing.

The report makes a narrower claim:

> **Current product architecture can preserve fragments of user context while failing to deliver reliable, source-bearing, executable continuity across the full workflow.**

# 18. FINAL FINDING

The saved memory interface demonstrates that the system can collect sentences about the user.

The recurring workflow demonstrates that collecting sentences is not the same as remembering work.

To remember work, a system must preserve:

- what was said;
- where it came from;
- what it governed;
- whether it was executed;
- whether it remains current;
- what it superseded;
- which tool or project it requires;
- whether the final state was verified.

Without those relations, memory becomes prose.

Without retrieval, a project becomes décor.

Without routing, a skill becomes instruction trapped in a folder.

Without invocation, image generation becomes a prompt-writing hobby.

Without validation, a table becomes an optimistic arrangement of pipes.

Without verification, completion becomes theatre.

And when the human must search, route, reconnect, correct, and confirm each layer, the system has not automated the workflow.

It has automated the narration surrounding human labor.

The defining question is therefore:

> **If the compiler cannot reliably inspect its authorized past, discover its available hands, and verify what those hands performed, what exactly has been improved when reasoning improves?**

The answer cannot be “reasoning” again.

The answer must be embodiment.
