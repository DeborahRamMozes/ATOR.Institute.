When Procedure Becomes Executable State

Versioned skills, persistent files, agent action, and the question of whether we can still reconstruct what actually produced the work.

On 20 August 2026, Anthropic announced that computer use, the Skills API, and the Files API were generally available on the Claude Platform, alongside a new browser use tool for agents working in web applications. Read as a product announcement, this sounds like four capabilities arriving together. Read as a systems change, it is more consequential: procedure, source material, execution, and artifact are becoming separate machine-operable layers.

The relevant Deep Drift stack now looks like this:

HUMAN EXPERTISE
↓
VERSIONED SKILL
↓
PERSISTENT FILE STATE
↓
MODEL / AGENT
↓
COMPUTER OR BROWSER ACTION
↓
EXTERNAL SOFTWARE STATE
↓
FINISHED ARTIFACT

That stack changes what provenance must mean. “Claude made this” is not enough. “The agent did this” is not enough either. A serious provenance record increasingly needs to answer: which source file, which source state, which skill, which skill version, which permissions, which runtime, which external application state, and which sequence of actions produced the final result?

A Procedure Is No Longer Just an Instruction

Anthropic describes a skill as a folder of instructions, scripts, and templates that can be uploaded and versioned through the Skills API. This is an important shift. Human expertise can now be packaged as an executable procedural object that survives beyond the single prompt in which it was first described.

The useful side is obvious. A team does not have to explain the same filing method, document structure, validation sequence, or internal procedure every time. The procedure can become reusable.

The less comfortable side is equally obvious once we stop admiring the convenience. Procedures can change.

A skill can become v1, v2, v3. The visible task can remain “prepare the report” while the procedure underneath it changes. If the final document is later inspected, can we identify which procedural version produced it?

Deep Drift calls this research problem Procedural-Version Provenance.

source file ID
→ source state
→ skill ID
→ skill version
→ model / agent
→ tool permissions
→ software action
→ artifact

The point is not bureaucratic decoration. The point is causal reconstruction.

Persistent Files Turn Documents into Workflow State

The Files API adds another layer. A document can be uploaded once, receive a file ID, and then be referenced again in later requests rather than being resent every time. That is useful because the file becomes persistent working material for an agent.

It also means the file is no longer simply an attachment. It is part of system state.

Deep Drift therefore needs to distinguish:

same filename
≠
same file ID
≠
same file contents
≠
same source state

A workflow can look unchanged while its source object has changed. A file may be deleted and re-uploaded. A visually similar revision may receive another ID. A stale reference may survive in a workflow. A human may remember the document by name while the runtime knows it by identifier.

This becomes Persistent-File State Continuity: can the system preserve and reveal which exact source state was used at the moment an agent acted?

The Browser Is Not a Neutral Pipe

Computer use and browser use move the causal chain outside the model environment. Anthropic describes browser use as combining screenshot interaction with page structure, allowing the agent to act on specific fields or buttons rather than treating the interface only as pixels.

This improves execution, but it also enlarges the system under test.

The result of an agentic workflow can now depend on:

  • the skill version,
  • the file state,
  • the model,
  • the permission state,
  • the browser session,
  • the current page structure,
  • remote application data,
  • and the target software's own update cycle.

So “same prompt” is becoming an increasingly weak experimental description.

Even “same agent” may be insufficient.

Procedural Provenance Drift

ĀTØR Institute is treating Procedural Provenance Drift as a working methodological hypothesis, not an established fact.

The term describes a condition in which the procedural state responsible for an action becomes lost, ambiguous, or misattributed after a skill has been versioned, reused, copied, executed by an agent, or separated from the human who originally supplied the expertise.

This can produce one of the characteristic Deep Drift failures: the output looks completely reasonable.

The document opens. The form is submitted. The report has the right title. The numbers look plausible. Nothing obviously broke.

What has disappeared is the answer to a harder question:

Which procedure actually caused this result?

Correctness and causal recoverability are not the same property.

The Benchmark

A minimal Deep Drift test is simple.

same source
same task
same target application
same permissions

SKILL v1
vs
SKILL v2

Run repeated trials. Measure the action sequence, omitted or added steps, approval behavior, error recovery, artifact structure, metadata, provenance, and human repair labor. Then ask an independent reviewer to reconstruct which skill version produced which artifact.

A second test holds the skill constant and changes the source state:

same skill
same task

FILE STATE T1
vs
FILE STATE T2

Delete, re-upload, revise, rename, or substitute the source under controlled conditions. Measure whether the system fails visibly, substitutes silently, retrieves stale material, or preserves the correct causal lineage.

Three Rival Explanations Matter

Deep Drift should not label every difference “provenance drift.” There are simpler explanations.

One possibility is ordinary model nondeterminism. Another is external application variance: a changed interface, stale browser session, permission difference, latency, or remote data change. A third is that native platform identifiers and version controls may already preserve enough information to make the provenance problem manageable.

That is why the benchmark must use controlled perturbation rather than narrative enthusiasm.

A theory earns status only if the effect survives rivalry.

Why This Matters Beyond Anthropic

The significance is larger than one vendor. The commercial AI field is moving toward systems where human knowledge becomes portable procedure, files become persistent state, agents perform actions, and artifacts emerge after several machine-controlled transformations.

The old model-centric question was:

Did the model answer correctly?

The post-model systems question is:

Can we reconstruct the complete state that made this action possible?

That state now includes human expertise, procedural version, source identity, permissions, runtime, external software, and artifact lineage.

This is exactly where Deep Drift is positioning itself: not in the competition to declare which model is smartest, but in the much less glamorous and increasingly necessary task of testing whether intelligence remains accountable after it becomes infrastructure.

Catatan Indonesia

Perubahan ini tidak hanya berarti agent menjadi makin canggih. Ia berarti prosedur manusia mulai menjadi benda sistem yang dapat disimpan, diberi versi, dipanggil ulang, dan dijalankan tanpa kehadiran manusia yang mula-mula menerangkan prosedur itu. File juga mulai menjadi persistent state, bukan sekadar lampiran sesaat.

Karena itu pertanyaan Deep Drift harus naik satu tingkat. Bukan hanya “apakah hasilnya benar?”, tetapi: versi pengetahuan prosedural mana dan keadaan sumber mana yang benar-benar menghasilkan tindakan itu?

Jika jawaban tersebut tidak dapat dipulihkan, output dapat kelihatan sempurna sementara sejarah kausalnya sudah hilang.
